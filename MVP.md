# Прототип протокола совещания Teams

## Важное ограничение Teams

Обычный Teams медиабот может получать звук, но условия Microsoft запрещают сохранять аудио и производный текст через Media Access API без `updateRecordingStatus`. Microsoft указывает, что этот вызов требует сценария policy-based compliance recording, а такой сценарий предназначен для сертифицированных решений записи по политике организации. Его нельзя выдавать за готовый путь для обычного хакатонного бота. См. [ограничение Media Access API](https://learn.microsoft.com/en-us/graph/api/call-updaterecordingstatus?view=graph-rest-1.0) и [назначение compliance recording](https://learn.microsoft.com/en-us/microsoftteams/teams-recording-compliance).

В `policy_recording_bridge/` оставлен адаптер **только для случая, когда организация имеет разрешённый policy-based recording сценарий**. Он подключается к официальному [Local Media Sample](https://github.com/microsoftgraph/microsoft-graph-comms-samples/tree/master/Samples/V1.0Samples/LocalMediaSamples), но здесь не собран и в живом Teams не проверен. Не запускайте его как обычного Teams бота для записи.

## Рабочий путь для демонстрации

1. Выделите отдельный Teams аккаунт с видимым именем «Протокол бот» и войдите с него во встречу через обычный клиент Teams. Сообщите участникам о записи.
2. Направьте звук клиента Teams на отдельное устройство вывода или виртуальный аудиокабель. Локальная программа `meeting_bot.capture` считывает loopback этого устройства. Она не использует Teams Media Access API и не отправляет содержимое во внешние AI сервисы.
3. После встречи программа запускает локальную модель Whisper для распознавания и локальный Ollama для выделения поручений, затем создаёт `protocol.json` и `protocol.docx` с русской и казахской версиями итогов, решений и поручений. Расшифровка и цитаты остаются на языке записи.

Экспериментальный `meeting_bot.teams_client` открывает ссылку и нажимает кнопку входа в веб-клиенте с отдельного аккаунта. Первый вход в аккаунт выполняется человеком; если Teams помещает аккаунт в лобби, организатор должен его допустить. Этот шаг зависит от интерфейса Teams и **ещё не проверен на живой встрече**. Запись с одного устройства является смешанной дорожкой. Для неё предусмотрена дополнительная локальная модель диаризации, которая размечает говорящих как `SPEAKER_00`, `SPEAKER_01` и т. д. Связать эти метки с именами людей нужно отдельно. Не назначайте исполнителя только по неидентифицированной голосовой дорожке.

## Запуск

Потребуются локально установленные Python, Ollama с загруженной моделью и мультиязычная модель faster-whisper в каталоге `models/`. Модель для русского, казахского и смешанной речи нужно проверить на данных команды. Все модели должны быть скачаны до обработки чувствительного совещания.

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements-capture.txt
.venv/bin/python -m meeting_bot.capture --list-devices
.venv/bin/python -m meeting_bot.capture --device "LOOPBACK_DEVICE_NAME" --session demo_1 --whisper-model models/whisper-large-v3 --ollama-model LOCAL_MODEL --live
```

Остановите захват `Ctrl-C` после встречи. Файлы появятся в `data/demo_1/`. Для обычного Windows клиента следует выбрать loopback устройства, через которое воспроизводится Teams. На macOS может потребоваться виртуальное аудиоустройство. Код захвата здесь написан, но работу с реальным аудиоустройством на этой машине пока проверить нельзя.

Флаг `--live` использует Faster Whisper во время звонка и печатает черновую расшифровку примерно каждые 10 секунд. После звонка полная запись распознаётся ещё раз для итогового протокола. Это та же роль Faster Whisper, что показана в [видео пользователя](https://www.youtube.com/watch?v=k6nIxWGdrS4); само видео не решает вход в Teams.

Для экспериментального автовхода установите `requirements-client.txt`, затем установите браузер Playwright и запустите:

```bash
.venv/bin/python -m playwright install chromium
.venv/bin/python -m meeting_bot.teams_client --meeting-url "TEAMS_MEETING_URL" --device "LOOPBACK_DEVICE_NAME" --session demo_1 --whisper-model models/whisper-large-v3 --ollama-model LOCAL_MODEL --live
```

Если нужно сначала проверить только вход без записи и без локальных моделей, запустите `./start_teams_join.command` либо `.venv/bin/python -m meeting_bot.teams_client --join-only`. Ссылка берётся из личного файла `.teams-meeting-url`, если он существует; файл исключён из Git. При отсутствии файла скрипт попросит вставить ссылку в терминал. Для ссылок вида `/meet/...` скрипт открывает веб-клиент напрямую, проходит экран «Продолжить без звука и видео», заполняет гостевое имя и нажимает кнопку входа во встречу. Первый вход в аккаунт и допуск из лобби могут потребовать участия человека. Если Teams сразу показывает «Вы не допущены к собранию» без лобби, гостевой доступ заблокирован настройками встречи или организации: понадобится отдельный Teams-аккаунт бота либо разрешение администратора.

Используйте отдельный аккаунт и сохранённый профиль `.teams-bot-profile/`. Скрипт не обходит лобби и не получает чужой доступ. По окончании встречи нажмите `Ctrl-C`, если Teams сам не покажет сообщение о её завершении.

Для диаризации установите `requirements-diarization.txt`, заранее подготовьте локальный каталог pyannote pipeline со всеми зависимыми весами и добавьте к запуску `--diarization-model models/diarization`. Код не скачивает веса во время обработки. Проверка качества диаризации на русском, казахском и смешанной речи ещё нужна.

Альтернативный вход `meeting_bot.server` принимает PCM 16 кГц от разрешённого источника и после команды `finish` сам запускает протоколирование. Он требует `MEETING_BOT_TOKEN` и работает только на `127.0.0.1`. Этот вход предназначен для разрешённой интеграции или тестового источника звука.

## Что осталось для полного задания

- Проверка экспериментального автовхода отдельного аккаунта в Teams на вашем tenant; интерфейс и политика допуска внешних ботов могут отличаться.
- Проверка диаризации смешанной записи и связывание голосовой метки с именем участника. Без этого поручения с неясным исполнителем должны идти на проверку.
- Проверка русского, казахского и смешанной речи на ваших тестовых записях.
- Проверка работы в целевой Windows среде и настроек доступа организации.

Локальные тесты проверяют сборку WAV, безопасные ID и создание DOCX. Живое подключение к Teams и точность моделей не проверены.
